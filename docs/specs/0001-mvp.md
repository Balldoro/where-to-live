# Spec: "Where to live?" MVP

> Status: ready for work. Test seams are **not yet established**; see Testing Decisions.

## Problem Statement

People choosing where to buy or rent a home in Poland judge a place with information that is spread across many sources, if they check at all. To answer "what is it actually like to live here?" they have to look at a map for shops, check transit apps for stops and lines, find a flood map on a government portal, and look up air quality on another site. Nothing brings this together for a specific address, and nothing is honest about where data is missing. When they have narrowed things down to a few flats, they have no simple way to keep those places or send them to a partner or family member for a second opinion.

## Solution

A web app covering all of Poland. The user types an address or drops a pin on a map, which gives a **Candidate location**. The app shows everything that matters around it on the map:

- the 10-minute **Walking catchment**
- **Amenity** pins inside it, grouped by **Amenity category**
- nearby public transport stops with the lines that serve them
- whether the place is in a **Flood zone**
- the latest **Air quality reading**

Wherever timetable data is missing, the app says so (no **Coverage**) instead of showing zero. Users can place their **Anchors** (work, school…) on the map. Browsing needs no account. Signing in with Google or GitHub lets users keep **Saved locations** and create a **Share link** for any of them. The recipient opens the link without an account and sees the place and the owner's Anchors, with everything else computed fresh.

## User Stories

### Finding a Candidate location
1. As a home seeker, I want to type an address and get suggestions as I type, so that I can find the place I'm considering quickly.
2. As a home seeker, I want suggestions to understand Polish addresses (ul., al., os., diacritics or no diacritics), so that I don't have to spell things exactly.
3. As a home seeker, I want to tell apart places with the same name in different parts of Poland, so that I pick the right one.
4. As a home seeker, I want to drop a pin anywhere on the map, so that I can evaluate a place that has no exact address yet (e.g. a new development).
5. As a home seeker, I want to drag the pin to adjust it, so that I can fix an inaccurate position.
6. As a home seeker, I want the map to fly to my Candidate location once I've chosen it, so that I immediately see the area.
7. As a home seeker, I want to replace the Candidate location with a new search or pin at any time, so that I can check several places one after another.
8. As a home seeker, I want a clear message when I place a pin outside Poland, so that I understand why no data appears.
9. As a home seeker, I want the Candidate location to be kept in the URL, so that reloading the page doesn't lose it.

### Walking catchment
10. As a home seeker, I want to see the area I can reach on foot in 10 minutes drawn on the map, so that I understand what "nearby" really means here.
11. As a home seeker, I want the catchment to follow real streets rather than a circle, so that a railway or river between me and a shop is taken into account.
12. As a home seeker, I want Amenities and stops to be judged by the same catchment, so that "nearby" means one thing across the app.

### Amenities
13. As a home seeker, I want to see pins for grocery stores, pharmacies, doctors/clinics, kindergartens/schools, restaurants/cafés, cinemas, parks, gyms and parcel lockers within the catchment, so that I know what everyday life here looks like.
14. As a home seeker, I want each Amenity category to have its own recognisable icon and colour, so that I can scan the map at a glance.
15. As a home seeker, I want to toggle each Amenity category on and off, so that I can focus on what matters to me.
16. As a home seeker, I want a count per category (e.g. "4 grocery stores"), so that I get a summary without counting pins.
17. As a home seeker, I want pins to group together when they overlap and split apart as I zoom in, so that busy areas stay readable.
18. As a home seeker, I want to hover or tap a pin to see its name and category, so that I know what it is.
19. As a home seeker, I want a clear "none within 10 minutes" state for a category, so that I can tell "nothing here" apart from "still loading".

### Public transport stops
20. As a home seeker, I want to see the public transport stops within my catchment on the map, so that I know how I'd get around without a car.
21. As a home seeker, I want to see which lines serve each stop (e.g. "trams 9, 22, 24; bus 131"), so that I can judge where I could get to.
22. As a home seeker, I want to tell trams, buses, trains and metro apart on the map and in lists, so that I understand what kind of service each stop has.
23. As a home seeker, I want a stop that appears in several operators' data (e.g. a railway station) to show up once with all its lines, so that I'm not confused by duplicates.
24. As a home seeker, I want to be told clearly when there is no timetable data for this area, so that I don't wrongly conclude there is no public transport.
25. As a home seeker, I want to tell "no stops within 10 minutes" apart from "no data for this area", so that I can trust what the app says.
26. As a home seeker, I want to see how fresh the timetable data is, so that I know whether to rely on it.

### Flood zones
27. As a home seeker, I want to know whether my Candidate location lies in a mapped Flood zone, so that I can avoid a costly risk.
28. As a home seeker, I want to see which flood scenario applies (e.g. a flood expected once every 10, 100 or 500 years), so that I understand how serious the risk is.
29. As a home seeker, I want to see Flood zones drawn on the map around my location, so that I can see how close the risk is even if I'm just outside it.
30. As a home seeker, I want the app to say "not in a mapped Flood zone" rather than "safe", so that I'm not misled where official maps don't cover.
31. As a home seeker, I want a link to the official source of the flood data, so that I can check it myself.

### Air quality
32. As a home seeker, I want to see the latest Air quality reading for my area, so that I can consider pollution (e.g. winter smog) in my decision.
33. As a home seeker, I want to see which monitoring station the reading comes from and how far away it is, so that I can judge how relevant it is.
34. As a home seeker, I want the reading shown on the standard Polish air quality index scale with colours, so that I can read it at a glance.
35. As a home seeker, I want to see when the reading was taken, so that I know it's current.
36. As a home seeker, I want a clear message when no station is reasonably close, so that I'm not shown a misleading number.

### Anchors
37. As a home seeker, I want to add Anchors (e.g. "Work", "Mum's", "School") by searching for an address or dropping a pin, so that I can see where I'd need to travel.
38. As a home seeker, I want to label each Anchor, so that I recognise it on the map.
39. As a home seeker, I want my Anchors shown on the map together with the Candidate location, so that I can see how far apart they are.
40. As a home seeker, I want to enter Anchors once and have them appear with every Candidate location, so that I don't re-enter "Work" for each flat.
41. As an anonymous home seeker, I want my Anchors remembered in this browser, so that I don't lose them when I come back.
42. As a home seeker, I want to edit and delete Anchors, so that I can keep them current.
43. As a signed-in user, I want my Anchors stored in my account, so that I see them on any device.
44. As a user signing in for the first time, I want the Anchors I made while anonymous to move into my account, so that I don't lose them.
45. *(Stretch)* As a home seeker, I want to see walking, cycling and driving times from the Candidate location to each Anchor, so that I can judge the commute.

### Accounts
46. As a home seeker, I want to use every evaluation feature without signing in, so that I can try the app with no commitment.
47. As a home seeker, I want to sign in with Google or GitHub, so that I don't need to create another password.
48. As a signed-in user, I want to stay signed in across visits, so that I don't have to sign in every time.
49. As a signed-in user, I want to sign out, so that I can use a shared computer safely.
50. As a signed-in user, I want to delete my account and all my data, so that I stay in control of my information.

### Saved locations
51. As a signed-in user, I want to save the current Candidate location, so that I can return to it later.
52. As a signed-in user, I want to give a Saved location a name (e.g. "Mokotów 2-room, 3rd floor"), so that I can tell my saved places apart.
53. As a signed-in user, I want a list of my Saved locations, so that I can move between them.
54. As a signed-in user, I want opening a Saved location to show the latest data around it, so that I always see current information.
55. As a signed-in user, I want to rename and delete Saved locations, so that my list stays tidy.
56. As a signed-in user, I want only me to be able to see my Saved locations, so that my house hunt stays private.
57. As an anonymous home seeker, I want to be asked to sign in when I try to save, so that I understand why an account is needed.

### Share links
58. As a signed-in user, I want to create a Share link for a Saved location, so that my partner or family can see the place.
59. As a signed-in user, I want the Share link to include my Anchors, so that the recipient understands the commute context.
60. As a signed-in user, I want to revoke a Share link at any time, so that I control who can see my plans.
61. As a signed-in user, I want to see which of my Saved locations currently have active Share links, so that I know what I've shared.
62. As a Share link recipient, I want to open the link without an account, so that I can look immediately.
63. As a Share link recipient, I want to see the same map view (catchment, Amenities, stops, Flood zone, air quality) computed fresh, so that I get current information.
64. As a Share link recipient, I want to see clearly that the page is read-only and shared by someone else, so that I'm not confused.
65. As a Share link recipient, I want a revoked or invalid link to show a clear "this link is no longer available" message, so that I know what happened.
66. As a signed-in user, I want Share links to be impossible to guess, so that nobody can browse other people's shared places.

### Fair use and reliability
67. As a home seeker, I want a friendly message when I'm making requests too quickly, so that I understand why results paused.
68. As a signed-in user, I want a higher usage limit than anonymous visitors, so that heavy research isn't blocked.
69. As a home seeker, I want a clear, friendly message when a data source is temporarily unavailable, so that the rest of the page still works.
70. As a home seeker, I want results for a place I just looked at to load quickly, so that jumping back and forth feels instant.

### Privacy and analytics
71. As a visitor, I want to be asked before analytics cookies or session recording are used, so that my privacy choices are respected.
72. As a visitor, I want the app to work fully if I decline analytics, so that consent is a real choice.
73. As a visitor, I want anything I type to be hidden in session recordings, so that addresses and personal details aren't captured.

### Operator
74. As the operator, I want timetable feeds checked nightly and re-imported only when they change, so that stop and line data stays fresh at low cost.
75. As the operator, I want a feed that fails validation not to replace the last good data, so that one broken feed never breaks the app.
76. As the operator, I want imports to become visible all at once, so that users never see half-imported data.
77. As the operator, I want a view of each feed's last successful import, freshness and validation status, so that I can spot silent failures.
78. As the operator, I want to be alerted when a scheduled import doesn't run or fails, so that I can react before data goes stale.
79. As the operator, I want the Amenity data refreshed monthly from OpenStreetMap, so that new shops appear.
80. As the operator, I want Air quality readings fetched hourly and stored, so that the app doesn't depend on the source being online at request time.
81. As the operator, I want a global daily limit on paid map-provider calls, so that the public app can never go past the free tier.
82. As the operator, I want errors from the frontend, the API and the import workers reported in one place, so that I can fix problems quickly.
83. As the operator, I want failed import jobs retried automatically, so that short-lived source outages fix themselves.
84. As the operator, I want to deploy with one command from CI, so that shipping stays cheap and repeatable.

## Implementation Decisions

### Architecture
- **Frontend:** single-page app (Vite + React, TanStack Router, TanStack Query) using Mapbox GL JS for the map, built to static files and served by Caddy on the same origin as the API (see ADR 0003). It talks only to our own API, except that map tiles load directly from Mapbox with a public token restricted to our domain.
- **Backend:** Python API (FastAPI) with PostgreSQL + PostGIS as the main store. Redis serves three purposes: rate limiting, caching, and the job queue.
- **Workers:** a separate process type running an arq job queue on Redis. A scheduler adds the import jobs to the queue: timetables nightly (skipped when nothing changed), Amenities monthly, Air quality hourly, Flood zones on demand or once.
- **Deployment:** one VPS running Docker Compose, with Caddy in front handling TLS. CI runs lint, type checks and tests, then deploys.
- **Tooling:** uv, ruff, mypy, Alembic for migrations. An OpenAPI schema generates the TypeScript types the frontend uses.

### Modules
- **Provider interfaces (deep modules hiding outside services):** Geocoder (search-as-you-type, reverse), IsochroneProvider (walking catchment), DirectionsProvider (stretch), AirQualitySource, FloodZoneSource, OAuthProvider. The first implementations are Mapbox, GIOŚ, ISOK WFS, Google, and GitHub. The frontend never calls these services directly (see ADR 0001), so any of them can be replaced.
- **Place evaluation:** takes a point and returns the Walking catchment, Amenities by category, stops with lines and mode, Coverage status, Flood zone result, and Air quality reading. The main page and Share links use the same evaluation.
- **Timetable ingestion:** downloads each registered GTFS feed, validates it, loads it into staging, merges duplicate stops across feeds into one stop with all its lines, records Coverage per feed, then switches staging to live atomically.
- **Amenity ingestion:** imports the OSM Poland extract, maps OSM tags to our fixed Amenity categories, and switches to the new data atomically.
- **Flood zone ingestion:** imports the ISOK flood hazard map layers per scenario, converting coordinate systems where needed.
- **Air quality ingestion:** fetches station locations and latest readings every hour and stores them.
- **Identity:** OAuth sign-in, database-backed sessions in an httpOnly cookie, and account deletion.
- **Saved locations and Share links:** create, read, update and delete, restricted to the owner. Share links use random tokens that can't be guessed, can be revoked, and have a public read-only view.
- **Anchors:** user-owned; stored in localStorage when anonymous and in the account when signed in. They move into the account on first sign-in.
- **Usage limits:** Redis-backed limits per IP (anonymous) and per user (higher), plus a global daily cap on Mapbox calls. When the cap is reached, the affected features degrade gracefully and the rest of the page keeps working.

### Domain rules
- **Walking catchment:** fixed at 10 minutes for the MVP and computed by the IsochroneProvider. Amenities and stops are "near" only if they fall inside it.
- **Coverage:** an area without timetable data is **unknown**, never zero. "No stops" and "no data" are different states in the API and the UI. There is no third-party fallback (ADR 0002).
- **Flood zone:** results are "in zone (scenario)" or "not in a mapped zone", never "safe".
- **Air quality reading:** always returned with the station name, the distance to it and the time of measurement. If the nearest station is further than a set limit, the result is "no nearby station".
- **Share link content:** a stored reference to one Saved location plus the owner's Anchors. Everything else is recomputed when the link is viewed. No snapshot is stored.
- **Mapbox licensing (ADR 0001):** temporary geocoding results are never stored. Isochrone responses are cached only briefly in memory or Redis and never kept in the database. Our own computed results (e.g. the Amenities in a catchment) may be cached in Redis.

### Schema (outline, not final)
- The OSM import populates `amenities` (point geometry, category, name, OSM id).
- `stops` holds merged stops (point geometry, name, mode(s)). A link table connects each stop to the feeds and the lines (with mode) that serve it.
- `feeds`: source URL, last checked, last imported, validation status, coverage area.
- `flood_zones`: polygon geometry and scenario.
- `air_quality_stations`, plus their latest readings.
- `users`, `sessions`, `anchors`, `saved_locations`, `share_links` (token, revoked_at).
- All geometry columns have a GiST index. Coordinates are stored as GPS latitude/longitude (SRID 4326); distances are computed in metres, using geography or the Polish metre-based coordinate system (SRID 2180) as appropriate.

### API (outline)
- Search for an address / reverse-geocode a point.
- Evaluate a point: returns catchment, Amenities, stops, Coverage, Flood zone and air quality. It may be split into separate parts so each can load and fail on its own.
- Anchors: create, read, update, delete (signed-in users).
- Saved locations: create, read, update, delete (signed-in users).
- Share links: create, list, revoke; public read by token.
- Sign-in start, OAuth callback, sign-out, and the current user.
- Import health: operator only.

### Observability and analytics
- Sentry covers the frontend, the API and the workers, with a cron monitor on every scheduled import.
- PostHog runs on EU Cloud. It uses no cookies until the user consents, shows a consent banner, and records sessions only after consent, with all inputs masked. **The PostHog configuration still has to be done. Which events and funnel to track is not decided yet.**

## Testing Decisions

**The test seams have not been established yet. This must be decided before implementation starts.**

Good tests check the behaviour a user or client sees, not implementation details.

A candidate proposal was discussed and **not yet accepted**:
- The main seam is the backend HTTP API, tested against a real PostGIS and Redis in containers. Outside services are faked only at the provider interfaces.
- Pipelines run on small fixture data (e.g. two tiny GTFS feeds sharing a stop), and the results are checked through the API.
- A thin layer of Playwright smoke tests covers the main paths, with Mapbox requests intercepted.

There is no earlier test code in the repo to build on, because the project hasn't started yet.

## Out of Scope

- Public transport commute times (MOTIS) and any timetable-based routing; how a commute is measured within a Time window is also undecided.
- Service level (departures per hour per Time window).
- A weighted score for how liveable a place is.
- Walking catchment calculated with our own pgRouting; a catchment size the user can change (5/10/15 min).
- Notes on Saved locations.
- Sharing a whole list of locations (a Share link covers exactly one Saved location).
- Email/password sign-in.
- Temperature and climate data.
- Any fallback to Google or other third-party transit data.
- Countries other than Poland.
- Actions on Amenity pins beyond viewing (e.g. details, routing to them).
- Native mobile apps.
